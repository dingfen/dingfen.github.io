Step-5 区域选择：只剩 511 项有效历史时，top-k 为什么反而最慢

更新于：2026-11-22T20:10:25+08:00

Step-5 选历史区域时，为什么只剩 511 项反而最慢？

有一批 decode 输入，每行分数预留了 131080 列，却只有前 511 个历史区域有效。Step-5 最多能保留 512 个历史区域，这 511 个本来都能留下。原实验里，旧链路处理这样一批数据要 562.3 µs。有效历史增加到 513 个时，原稿测出的耗时反倒降到了约 177 µs。

这里能省三遍工作：top-k 只扫有历史的列，打分时顺手处理正负零，选完直接沿用已经排好的 ID。下游还要查 KV 页表，这一步也能并入最后一次写回。

把有效长度交给 top-k

原因藏在接口里。原先调用 FlashInfer 的普通 top-k，只传了矩阵宽度。对库来说，每一行都有 131080 个候选。后面十几万项虽然都是代表“未来”的负无穷，也要参加筛选。只有 511 个有效项时，连第 512 个名额都落进了大量同分的负无穷里。

每行到底有多长，模型早就知道。在这条路径上，一个 region 占 8 个 token，位置除以 8 就得到当前行之前的完整 region 数。新实现把它限制在矩阵宽度以内，padding 行填零，然后将这些长度传给 top_k_ragged_transform。长度直接在设备上生成，graph 重放时不必把位置读回 CPU。现在，同一行只需查看前 511 项。单看 profiler 里的 top-k kernel，耗时从 549 µs 降到 1.82 µs。生成长度、整理 ID 和写输出仍有各自的成本。

分数只写一次，选出来的 ID 只排一次

原实现还会复制整张分数表，把里面的 -0.0 统一成 +0.0。数值比较时两者相等，但这条 top-k 路径会先把浮点比特映射成整数排序键，正零和负零可能得到不同的键。同分时取哪个 region 会影响后续注意力读哪段历史，所以正负零的处理得保留。

打分 kernel 本来就要写出每个分数，在写出前检查零的位模式即可。16 行、131080 列的例子里，这样省去了读一遍又写一遍约 8.4 MB 的 FP32 矩阵。另一个可以省下的步骤在 top-k 之后。原实验使用的 FlashInfer 确定性分支已经按 region ID 升序返回结果，无效 ID 排在尾部。_pack_regions 直接消费这个顺序，单次从 6.8 µs 降到约 1.9 µs。

读这组数据要区分“预留宽度”和“有效长度”。两者差得越远，可以跳过的工作越多。原稿中的 48 倍来自 511 项这个特定形状。上表测的是 FlashInfer 路径。

最后一次写回，可以顺手算出物理位置

选出的 ID 还是逻辑编号。decode 还需要知道它在 KV 池里的物理位置。早期实现先把 ID 写出去，紧接着再启动一次 kernel，把同一行读回来查页表。既然 _pack_regions 此时已经拿到了 ID，就可以在同一次调用里输出两份结果。

举例说，有 511 个历史区域时，前 511 个槽放历史 ID，第 512 个槽放当前位置。有 512 个历史区域时，当前位置要写到下标 512，也就是第 513 个槽。对每个有效槽，用 region_id × 8 查到物理 token 位置，再按下游约定把物理区域和逻辑偏移打包。输出缓冲区如果比 513 更宽，多出来的槽要清成 -1，否则下一轮可能读到上一批的地址。

在另一组 decode trace 里，两次打包调用合计每层 3.97 µs，合并后为 2.27 µs。这是打包阶段单独的前后对比。仓库的选择入口、打包实现和边界测试可以对照阅读。

后来的 PPU radix 路径：能全选时，连分数也不用读

前面 11.7 µs 的实验仍然调用了 FlashInfer。后来接入 PPU radix 选择器后，可以再往前问一步：如果本行只有 511 个历史区域，512 个名额足够全选，那么无论分数是多少，历史 ID 都是 0 到 510。单线程块和 streaming 两种选择器都能直接产生这串 ID，随后照常追加当前区域。

以三个同批请求为例，假设它们分别有 511、512、513 个历史区域。前两行直接保留所有历史；第三行要从 513 个里淘汰一个，仍然需要有效分数。compact 打分处理这个混合组时，只给第三行的有效列写分。如果整组都像前两行，加载 query 和矩阵乘都可以跳过。padding 行仍由请求槽位识别，最后计数为零。
