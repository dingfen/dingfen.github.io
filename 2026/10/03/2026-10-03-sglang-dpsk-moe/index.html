TL;DR

上篇博客我们介绍了 vLLM 上 DeepSeek V4 的 MoE 层 DeepGemm 相关实现，这篇博客我想走读一下 sglang 上 deepgemm MoE 层的 DeepGemm 使用。在 sglang 中，当 runner backend 选中 deep_gemm 后，整个前向是一套固定的流程，本文按 六大阶段 组织：

  1. 权重预处理阶段（加载期一次性）：权重与权重 scale 整理成 DeepGEMM 最终消费的布局；
  2. GEMM1 前：路由（TopK）→ dispatch → pre_permute，把 token 打成 grouped 布局并量化激活；
  3. GEMM1 计算：w13 的 grouped GEMM（gate/up 投影）；
  4. GEMM1 与 GEMM2 间：SiLU/SiTU 激活 + 下游激活量化（融合 kernel）；
  5. GEMM2 计算：w2 的 grouped GEMM（down 投影）；
  6. GEMM2 后处理：post_permute → combine → 模型尾部融合与归约。

2. 六大阶段拆解

2.1 ① 权重预处理阶段

这一块只在权重加载期执行一次（外加运行时对 quant_info 组装），目的是让 deep_gemm 在运行期只做纯 GEMM，不再碰权重布局。

2.1.1 谁触发了 deep_gemm runner

两个入口：一个在权重加载期，一个在runner 创建期。

  1. 加载期：Fp8MoEMethod.process_weights_after_loading_block_quant 的 CUDA 部分实现里，会先判断 deepgemm 是否会被使用 will_use_deepgemm = is_deepgemm_moe_runner_backend_enabled()。这个布尔值决定权重与 scale 是否按 DeepGEMM 所需布局预处理，（具体细节详见下文 2.1.2）。
  2. 运行期（runner 创建）：Fp8MoEMethod.create_moe_runner）：
    • auto：若 is_deepgemm_moe_runner_backend_enabled() 为真 → MoeRunnerBackend.DEEP_GEMM，否则 TRITON（:2764-2774）；
    • 显式 deep_gemm 等后端直接触发

is_deepgemm_moe_runner_backend_enabled（fp8.py:1334-1356）判定：

  • moe_runner_backend == DEEP_GEMM → True（显式指定）；
  • AUTO ∧ moe_a2a_backend ∈ {DEEPEP, MOONCAKE, NIXL} ∧ ENABLE_JIT_DEEPGEMM → True；
  • 否则 False。

另外两个来源的强制 / 例外：

  • deepep_v2 强制：runner.py:85-94 校验 deepep_v2 必须搭配 deep_gemm runner；
  • V4 例外（arg_groups/model_overrides/deepseek_v4.py:66-88）：nvfp4_moe_meta 时改为 flashinfer_trtllm_routed；fp4 experts ∧ a2a=none ∧ SM90/100/120 时改为 flashinfer_mxfp4；
  • SGLANG_DSV4_FP4_DEQUANT=1（fp8.py:414-418）：只允许 auto 起步（fp4 反量化成 fp8 运行的对照路径）。

2.1.2 四条权重路径

现在我们仔细看一下 Fp8MoEMethod.process_weights_after_loading_block_quant 的 CUDA 实现细节：

第一行 will_use_deepgemm = is_deepgemm_moe_runner_backend_enabled() 做判断，然后按权重类型分四条路。

路径 A：MXFP4 experts（Blackwell 默认路径，is_fp4_expert=True）

  1. 先把权重 view 成 int8（marlin / NPU / megamoe 各有早退分支）。
  2. if deep_gemm_wrapper.DEEPGEMM_SCALE_UE8M0 and will_use_deepgemm:，对 w13/w2 分别调用：

即把 (E, N, K/32) 的 fp32 scale 转成 DeepGEMM 要求的 MN-major、TMA 对齐、UE8M0 打包布局，并打 format_ue8m0=True。MXFP4 的 scale 本来就是 2 的幂，cast 无精度损失。输出的权重本体保持 int8 packed。

路径 B：FP4 反量化（SGLANG_DSV4_FP4_DEQUANT=1 ）为 FP8

代码会逐个 expert 调 cast_e2m1fn_to_e4m3fn(w[e], s[e])，把 fp4 无损转 fp8（e2m1 → e4m3 是精度扩展，最多补 6 个尾数位，MAX_OFFSET_BITS=6），它会先将 int8 中的 mxfp4 数据单独提取出来，分别做 dequant，然后将量化组改为 128 个一组，再重新扩展到 FP8 的量级 + offset。随后 format_ue8m0=False、self.is_fp4_expert=False，交回路径 C ，做通用 block-FP8 逻辑继续处理。

路径 C：普通 block-FP8（is_fp4_expert=False）

对 w13/w2 分别调用 requant_block_scale_ue8m0_for_deepgemm(...)。该函数的进入条件是四连与：

  • use_deepgemm_runner（确实选了 DeepGEMM runner）；
  • weight_block_size == [128, 128]（权重量化 kernel 只支持这一种）；
  • not format_ue8m0（尚未重排过）；
  • should_deepgemm_weight_requant_ue8m0(...)（加载器侧判定：输出 dtype、形状对齐是否满足）。

满足则 requant_weight_ue8m0_inplace → 对 3D MoE 权重做 requant，见 requant_weight_ue8m0，并走 _requant_weight_ue8m0_grouped，逐 expert 三步：

  1. block_quant_dequant：fp8 权重 + scale 还原为 bf16；
  2. quant_weight_ue8m0 → per_block_cast_to_fp8：重新按 128×128 block 量化成 fp8，scale 保持 fp32；
  3. transform_scale_ue8m0(out_s, mn=n)：先 index_select(-2, arange(mn)//128) 把 mn 方向 128 行共享一份 scale（MN-major packing 的粒度要求），再 get_mn_major_tma_aligned_packed_ue8m0_tensor 将 fp32 scale 打包成 UE8M0 int32、MN-major、TMA 对齐；返回时修复 DLPack 在 K ≤ 128×4 时塌缩的尾维 stride。

完成后 weight_scale.format_ue8m0 = True，运行时无需再转换。注意这是数值重量化（block 量化→反量化→重量化），目的是为了将 FP8 128 blockwise 的数据重新变为 DeepGemm 要求的 FP8 quant 类型，scale 粒度依然是 128x128，但 scale 存储会变为 MN-major packed 的 int32 存储方式。

路径 D：MXFP8（use_mxfp8=True）

最后我们来看 mxfp8 量化的处理方法，在 _process_mxfp8_moe_weights(layer, quantize=not is_checkpoint_fp8_serialized)。先平台断言：要求 SM100（或 ROCm gfx95）。随后按来源分两种：

  • quantize=True（checkpoint 非 fp8 序列化，需要权重在线量化）：
    • deep_gemm 分支 _quantize_for_deepgemm 把 (E, N, K) 拍平成 2D (E·N, K)
    • mxfp8_group_quantize 调用 triton 内函数，沿 K 轴每 32 个元素一组做标准 MX 量化
    • _ue8m0_to_fp32 把 8 位指数放回 fp32 的 exponent 位，得到"值为 2 的幂的 fp32"
    • _pack_moe_scale_for_deepgemm DEEPGEMM_SCALE_UE8M0 时走 get_mn_major_tma_aligned_packed_ue8m0_tensor 打包成 MN-major 的 int32 TMA 行对齐的 scale。
    • 一句话，就是将原先的权重变为了 deepgemm 需要的 FP8 quant 格式。
  • quantize=False（checkpoint 已是 MXFP8）：deep_gemm 分支 _convert_ue8m0_scales_for_deepgemm（:2342-2350 → :2264-2271）：u8 scale → fp32 → 同样打包。

结尾 _copy_or_rebind（形状/dtype 一致则原地 copy，否则重绑参数）并设置 format_ue8m0=True 表示权重已经完成处理。MXFP8 权重布局保持 (E, 2I, K) fp8 e4m3，仅 scale 变为打包布局。

注：MXFP8 的 weight_block_size 通常都是 [1, 32] 的颗粒度

2.1.3 运行时组装：DeepGemmMoeQuantInfo

每次前向 Fp8MoEMethod.apply 在 runner_backend.is_deep_gemm() 分支）组装量化信息：

  • block_quant（block-FP8 / MXFP8）：block_shape = quant_config.weight_block_size，scale 直接引用 w13_weight_scale_inv / w2_weight_scale_inv（2.1.2 已就绪）；
  • per-tensor（weight_block_size is None）时：把 per-tensor scale 展开成 block 伪 scale —— 这段代码关键，它将形状 (E, ceil(N/128), ceil(K/128))、block_shape=[128,128]。数值上每个 128×128 block 共享同一 per-tensor scale，这样做纯粹是为了让同一套 GEMM 接口吃下 per-tensor 检查点。

DeepGemmMoeQuantInfo 字段与约束：

__post_init__ 断言：use_mxfp8 必须 block_shape == [1, 32] 且 DEEPGEMM_SCALE_UE8M0=True。

关键方法 scale_recipes(...) 把字段翻译为 GEMM 的 A/B（激活/权重）recipe：

情形 返回 (A, B) 说明
use_mxfp8 ((1, activation_block_size), (1, 32)) 断言 ceil_div(K, ab*4) == activation_scale_width（打包后列数匹配）
is_fp4_experts ((1, 128), (1, 32)) 激活 fp8 每 128 一份；权重 fp4 每 32 一份

MXFP4 若走 Mxfp4MoEMethod.apply（mxfp4.py:1578-1606），则等价地硬编码 DeepGemmMoeQuantInfo(block_shape=[128,128], is_fp4_experts=True)，但实际 sglang 实现中没有加入 DeepGemm FP4 x FP4 的处理计算逻辑

另外记几个后续阶段会用到的 MoeRunnerConfig 字段（参考代码 moe_runner/base.py:37-69）：

  • swiglu_limit gemm1_clamp_limit float，对激活函数的输出值做一些限制，防止产生极大异常值甚至溢出。在低精度量化下，MoE 路由或矩阵乘法容易产生极大的异常值（Outliers）。如果不加限制，这些异常值会导致量化缩放因子（Scale）失调，甚至引发 FP8/FP4 计算溢出（Overflow）。强制钳位可以截断极端值，保障底层 MoE Kernel 的数值稳定性
  • gemm1_alpha float，SwiGLU 激活函数中 SiLU 部分的缩放系数
  • silu_mul_keep_fp32 bool，表示是否需要用 FP32 来表示 SiLU 结果
  • top_k int，MoE 路由后，决定每个 Token 被激活并分配给的 Experts 的数量
  • num_local_experts int，在当前并行策略下，当前卡分配到的本地 Experts 数量
  • intermediate_size_per_partition：int，当前并行策略下，Experts 的中间隐藏层大小

而 DeepEPMoE）在这里的角色是：当 deep_gemm runner + Fp8Config 组合下为 True（其余条件还包括 deepep_v2 / humming / aiter / npu 等）时， DeepEPMoE.forward_impl）会使用 super().forward_impl(...)，复用上面的现代三段式；否则才走它自带的旧式 dispatch/combine 实现。这就是为什么 DeepSeek V4 的 EP 形态最终与 FusedMoE 汇到同一段代码。

2.2.4 五种 pre permute 方式

1）standard：

  • 先处理 SM120：deep_gemm_sm120.maybe_pre_permute(...) 若命中直接返回；命中不了则 assert 拒绝，因为 SM120 DeepGemm 的 grouped GEMM 只能支持 standard-layout activation 布局。

  • masked 布局，处理后会直接喂给 DeepGEMM masked grouped GEMM，所谓的 masked grouped GEMM 接口可以看第三节对 DeepGEMM 的简介，简单来说 masked 接口是用内存换简单（小 batch / capture 默认），它给每个 Experts 分一个简单固定的内存空间，用不上的打 masked 遮掩，当条件允许时，moe_ep_deepgemm_preprocess 会一步完成“按 expert 对齐 slab + 激活量化”，产出 masked_m / src2dst / hidden / scale；以及 expected_m。他们分别指代：

    • masked_m：每个 local experts 分给真实有效行数，即 experts 对输入 在 3D 布局 [E_local, m_max, K] 中真正需要计算的行数。通过 fused_moe_dispatch_index_triton_kernel 计算得到
    • expected_m：每个 experts 在当前 hidden_states 的大小下分配到的 token 数的期望，调优 gemm 时使用
    • src2dst 记录 permute 过程中当前 rank 如何重排 token 的表，同样也是 fused_moe_dispatch_index_triton_kernel 计算得到

  • compact 布局 处理 DeepGEMM contiguous grouped GEMM，contiguous grouped GEMM 后面我们也有说到。在处理更大的 token 时，contiguous gemm 会更省内存（因为它只会保留真实有效的 token），token 也是按照 [M_total, K] 专家连续平铺。

    • get_contiguous_layout_alignment，DeepGEMM contiguous 布局要求的 MK 对齐（每个专家段的起始和长度都必须是它的倍数）。_get_compact_all_tokens(...)，这是在计算最坏路由下的 padding 上界，保证不会越界。

    • 返回 running_state：src2dst、all_tokens、contiguous_layout_alignment=block_e

2）flashinfer 部分不细聊了，它仅接受 BF16 未量化 dispatch，后转交 standard 实现。

接下来是针对 DeepEP 模式的处理，先回顾一个前提：三种 DeepEP 模式的差别，本质是 dispatch（all-to-all 收发）交给 pre_permute 的"半成品"长什么样。pre_permute 要做的，就是把这个半成品整理成 DeepGEMM 能直接使用的 DeepGemmRunnerInput——要么是 masked [E_local, m_max, K]，每 expert 一块固定空间、用 masked_m 标注真实行数，要么是 contiguous 平铺 [all_tokens, K]，各 expert 段紧挨着、用 m_indices 标注每行属于哪个 expert。

3）deepep_ll（低延迟模式）：dispatch 直接把结果摆成了 masked 布局，并一同计算了 masked_m 和 expected_m。所以这个函数几乎什么都不做，原样透传，设置 use_masked_gemm=True，activation_scale_block_size 固定写 128（LL dispatch 出口就是 128 分组的 FP8）即可。

4）deepep_normal（普通模式）：与 LL 相反，dispatch 只给"按到达顺序堆在一起的 token"，外加一个 num_recv_tokens_per_expert（每个 expert 各收到多少条）。这种显然与 contiguous 布局更接近，但需要自己把这些乱序 token 按 expert 重排成连续段：

  • 先算总量 all_tokens = sum(num_recv_tokens_per_expert)），据此分配输出激活缓冲 (all_tokens, K)
  • scale 形状分两种：Blackwell 的 UE8M0 走 int32 打包 + 列主序 (ceil_div(K//128,4), all_tokens).transpose(0,1)；其余走普通 fp32 行主序 (all_tokens, K//128)
  • ep_scatter 一步完成重排：把乱序 token 按 recv 计数散进连续段，同时产出 m_indices（行→expert）和 output_index（记下行原来在哪，回程时靠它把结果发回，存入），最后设置 use_masked_gemm=False。

5）deepep_v2：v2 dispatcher 在 GPU 上直接算好了每个 expert 的前缀和 每个 experts 要接收到的 tokens 数量 psum_num_recv_tokens_per_expert，并带两个开关：is_expanded（token 是否已在 dispatch 阶段展开到 topk 份、基本就位）和 use_masked_gemm。按这两个开关分三条路，目标都是凑出 masked 或 contig 输入：

  • is_expanded || use_masked：已展开的 token 只差填入到 masked 槽这一步，expand_to_masked_slab 直接把前缀和描述的数据变为 masked 3D 布局，产出 masked GEMM 输入
  • is_expanded || ¬masked：同样已展开，但要 contiguous 布局，于是只需给每行标 expert 号——ep_expand_init_m_indices_from_psum 按前缀和填 m_indices，尾部没用上的行留 -1
  • ¬expanded：token 还是乱序到达，退化成和 deepep_normal 一样的重排流程，只是散开时改用 v2 的前缀和 ep_scatter_from_psum，scale 缓冲的 UE8M0 / fp32 分配公式与 deepep_normal 完全相同。

到这一步，两种 GEMM 形态（masked / contig）与四种量化配方（bf16 / block-fp8 / mxfp8 / mxfp4）的输入都已备好，进入 GEMM1。

2.4 ④ GEMM1 与 GEMM2 间：激活与量化

GEMM1 返回的 gateup_output 是 (all_tokens, 2I) 或 (E, m, 2I) 的 bf16，而在一般量化情况下（FP8 / MXFP8 / MXFP4），GEMM2 的 A 侧不能是 BF16，必须已经量化处理后的。所以这一阶段只有两件事：做 gated 激活（把 gate / up 两半成 I 宽），以及做激活和量化。

为什么这两件事要挤进同一个 kernel？2I 因为如果 先算激活写回 bf16、再读回来量化 两步走，内存就需要多搬两遍；而融合 kernel 只读一遍 bf16、写一遍 fp8 与 scale，这也是为什么大家都在尽量将 kernel 融合的原因。

再强调一个贯穿全节的约束是 scale 的产出布局。GEMM2 的 A 侧 scale 由 deep_gemm 直接消费：在 UE8M0 类型下必须是 packed int32、MN-major、TMA 对齐（三条生产线的来历见附录 A）。

2.4.2 masked 形态：varlen 激活量化

masked 形态（deep_gemm.py:790-824）多一层麻烦：输入是 (E, m_pad, 2I) 的 slab，每个 expert 只有前 masked_m[e] 行是真实数据。激活 kernel 必须以 masked_m 为上界逐个 expert 跳行，也就是代码里的 varlen。

  • situ 走 _varlen_deep_gemm_situ_mul_quant，底层是 CUDA JIT 的 situ_and_mul_masked_post_quant，量化 group 在这里被直接改写成 128（deep_gemm.py:791-800）， SiTU 分支的激活量化粒度固定为 128；
  • 其余走 _varlen_deep_gemm_silu_mul_quant。进函数之前先算 num_real_tokens（deep_gemm.py:802-812）：只有 use_mxfp8、DEEPGEMM_SCALE_UE8M0、topk_ids、src2dst 四者齐备时才把真实 token 数传进去，因为只有“token 已展开且知道源行映射”的布局才真的数得清真实行；这个数用于把 kernel grid 限制在真实行上，避免按 padded_m 空转。

_varlen_deep_gemm_silu_mul_quant 内部还有三个子分支（deep_gemm.py:1559/1600/1634，打包细节见附录 A）：

  1. gemm1_alpha（oai-swiglu）：Triton 的 silu_and_mul_masked_post_quant_fwd，因为通用量化 kernel 还没有 activation-kind 这个维度，oai-swiglu 暂时只能留在 Triton 实现上。use_packed 需要同时满足 UE8M0、num_real_tokens 非空、G % 4 == 0、D % (group*4) == 0；packed 时先分配 (E, G//4, N) 的 int32，再 transpose(-1,-2) 把内存形态转成 MN-major。
  2. swiglu_limit / swizzle / silu_mul_keep_fp32（DSV4 主战场）：DSV4 JIT 的 silu_and_mul_masked_post_quant。这里有三条硬断言——N % 4 == 0、G % 4 == 0、D // 8 >= E（deep_gemm.py:1601-1604）：前两条是 packed scale 与向量化的对齐要求，最后一条来自 kernel 的线程编排——block 里开 D / 8 个线程，而 get_work 要用前 E 个线程各读一个 expert 的 masked_m 做前缀和，所以必须 D / 8 >= E。不满足就在激活量化处直接报错，没有退回其它分支的后路。scale 同样 packed + transpose(-1,-2)。
  3. 默认：通用的 per_token_group_quant（fuse_silu_and_mul=True、masked_m=...、expected_m=ceil_div(num_real_tokens*topk, E)、column_major_scales=True）。它自己分配输出，scale 直接落成 deep_gemm 消费的列主序布局，所以调用方在 GEMM2 前的 get_mn_major 变换会短路。注意这个通用 kernel 会把 SiLU 中间值 round 到 bf16——这正是上面 silu_mul_keep_fp32 存在的理由。

2.5 ⑤ GEMM2 计算

GEMM2 和 GEMM1 调的是同一族 grouped 接口，差别只是 A 侧换成了刚量化好的 down 输入、B 侧换成 (E, K, I) 的 w2、N 方向从 2I 变回 K。真正值得单独拎出来说的只有三处：输出进对称内存、A 侧 recipe 要重算、masked 形态还要承担 combine 的 overlap。

2.5.1 contig 形态（deep_gemm.py:597-626）

三处安排各有各的理由：

  • 对称内存：down_output 是 GEMM2 的输出，也是 core 前向里唯一进 NCCL symmetric memory pool 的张量（注释就写在 deep_gemm.py:593-596）：它是这条计算链里唯一要参与下游通信的结果，放进池里就能让 all-reduce / reduce_scatter 走低延迟的对称路径。gateup_output、down_input_fp8 这些中间 buffer 留在默认 allocator 上，是为了不让 pool 的占用被中间激活撑大。回程的 (M, H) 输出同理——post_permute_deep_gemm_to_standard 也把它分配在池里（deep_gemm.py:1260-1265）。
  • scale 再对齐：非 UE8M0（Hopper）平台刚量化出来的 down_input_scale 是行主序 fp32；GEMM1 前那次 tma_align_input_scale 只处理了输入激活，这里的 A 侧 scale 是新产出的，必须照同样规格转成列主序加 16 字节对齐。UE8M0 平台因为量化时已经直接产出消费布局，这一步自然跳过。
  • recipe 重算：scale_recipes 给出的 A 侧 recipe 依赖 K——GEMM1 的 K 是 hidden H，GEMM2 的 K 是 intermediate I，两者不同。对 MXFP8 而言它还顺带断言 ceil_div(K, 32*4) == activation_scale_width（打包后列数必须对得上），这个断言本身也得按新的 K 重新算一遍。

2.5.2 masked 形态（deep_gemm.py:830-896）

masked 形态同样把 (E, m, K) 的 down_output 放进对称内存（deep_gemm.py:855-860）：

并且额外多做了两件事：

  • scale 的最后一跳打包：use_mxfp8 且 DEEPGEMM_SCALE_UE8M0 且 down_input_scale 还不是 int32 时，此时需要调整 sacle 为 UE8M0 的格式，需要调 deep_gemm.get_mn_major_tma_aligned_packed_ue8m0_tensor（deep_gemm.py:833-844）。正常路径上各激活分支产出的已经是 packed int32，这一步是兜底；非 UE8M0 平台则走 wrapper 的 get_mn_major_tma_aligned_tensor（deep_gemm.py:845-848）。

  • combine 与 down GEMM 的双流 overlap：down_gemm_overlap_args 非空时先 start_event.record()，再根据平台不同选择合适的 block 数值，具体为 max_block_n = 160 if (H20 且 expected_m ≤ 64) else 256，连同 overlap_args 一起传给 GEMM。GEMM 分块计算，combine 在另一条流上等第一批 block 完成就开跑；

    这种 overlap 模式是将 GEMM2 和之后的 allreduce 做了通算重合，此时 GEMM2 的返回值是 (block_m, threshold)，这里原样写回的 meta_overlap_args，供 DeepEP 的 low_latency_combine 判断“前多少行已经算完、可以开始合并发送”。H20 上把 max_block_n 压到 160，这应该是一个经验值，H20 上计算的 N 方向的 tile 更小（因为算力小），于是第一批 block 就能更早完成，那么通算的 overlap 更容易真正叠起来。

两个形态还有一个共同收尾：GEMM1 用完的输入激活在 GEMM1 之后就被 dispose_tensor 掉了（contig deep_gemm.py:467-468、masked deep_gemm.py:783-784），也就是 §2.3.1 讲过的“把 storage 换成 0 字节空张量、立刻归还 caching allocator”。所以峰值显存基本只包含当前这次 GEMM 的输入与输出，而不是整条链路的中间激活之和。

2.6 ⑥ GEMM2 后处理

2.6.1 post_permute：五种回程

post_permute 和 pre_permute 是镜像关系：pre_permute 把 dispatch 的“半成品”整理成 grouped 布局，post_permute 则要把 grouped 结果还原成各 dispatcher 的 combine 能消费的形态。但回程比进料多了一道题——top-k 加权与 routed_scaling_factor 到底在哪一层计算。五种回程的差别，本质上就是这道题的五种答案：

dispatch_format post_permute 加权折叠位置
standard post_permute_deep_gemm_to_standard post_reorder_deepgemm 内，随 src2dst 累加一并乘
flashinfer post_permute_deep_gemm_to_flashinfer 复用 standard，再转成 bf16 payload
deepep_ll post_permute_deep_gemm_to_deepep_ll 留给 combine
deepep_normal post_permute_deep_gemm_to_deepep_normal ep_gather 内
deepep_v2 post_permute_deep_gemm_to_deepep_v2 expanded 分支在这里，非 expanded 在 ep_gather 内

standard 最典型：post_reorder_deepgemm 中使用 post_reorder_deepgemm_triton_kernel 按 src2dst 把同一 token 的 top-k 份结果累加回 (M, H)，并在写回时把 routed_scaling_factor 一并算进去，所以模型层不需要再单独做一次比例缩放。输出同样走对称内存，写完立刻 dispose_tensor 掉 GEMM 的大 buffer。

但在 SM120 上，：deep_gemm_sm120.maybe_post_permute 命中就直接返回，交给它自己的重排实现 ep_gather。

flashinfer 只是把 standard 的结果再包一层：它要求 payload 是 bf16，不是就直接 TypeError；转成 FlashinferCombineInput 之后，由 combine 侧的 A2A 完成回程。

deepep_ll 最短：dispatch 阶段就是 masked 布局、combine 阶段本来就要消费 topk_ids / topk_weights，所以这里原样透传，一个权重都不乘。

deepep_normal 把“收回 + 加权 + 归约”压进一次 ep_gather(hidden, topk_ids, topk_weights, output_index, gather_out)（deep_gemm.py:1477），output_index 就是 pre_permute 时 ep_scatter 顺手记下的回程映射。

deepep_v2 要看 dispatch 时 token 有没有展开，分三种情况：

  • 展开且 masked：masked_slab_to_expand 把 (E, m, H) 的 slab 按前缀和摊回每个 route 一行。这里还分两种模式：no_combine 时只做展开、不乘权重，把 topk_weights 一并交给 routewise finalizer；否则在 kernel 里把权重乘掉，combine 只负责求和：

  • 展开但不 masked：token 已经就位，而 expanded combine 不消费权重，所以这里显式做 hidden * topk_weights.unsqueeze(-1)（deep_gemm.py:1891-1896）。

  • 未展开：与 deepep_normal 同构。no_combine 时按 output_index >= 0 把结果沿 route 维散回 (M, top_k, H)、非本地 route 填 0（deep_gemm.py:1902-1919），否则就是 ep_gather。

2.6.2 combine 与模型尾部

回到 FusedMoE.forward_impl 的最后一步：dispatcher.combine(combine_input) 完成跨 rank 的合并与再通信，把结果还原成 (M, H)（fused_moe_triton/layer.py:1586-1589）。这一步同样要使用 NCCL Symm 技术，包裹在 use_symmetric_memory 里，combine 的输出直接落进 pool，然后 all-reduce 才能能走对称通信；出来之后再按入口记录的 origin_hidden_states_dim 切回原始宽度并 contiguous()（fused_moe_triton/layer.py:1592-1594）。

模型层的尾部（deepseek_v2.py:1368-1393）做三件事：

  1. routed 与 shared 相加：maybe_fuse_routed_scale_and_shared_add。这里要澄清一点：对 DeepGEMM 路径而言，routed_scaling_factor 已经在 post_reorder_deepgemm 里折进写回了，这个函数实际只做 routed += shared 的原地相加；函数里那套 alpha=routed_scaling_factor 的融合分支，是给 flashinfer trtllm 这类“把 scaling 融进 top-k 权重”的后端准备的。
  2. mhc 统计点与 post-experts 归约：DeepSeek V4 且 TP>1 时，会在归约前先给 mhc post fusion 打一个 start_stats_before_all_reduce() 统计点；随后 post_experts_all_reduce 把 EP 组与 MoE-TP 组的归约收在一次里（两者都生效时合并成一次 TP all-reduce，deepseek_v2.py:1385）。这一步会被 should_skip_post_experts_all_reduce(is_tp_path=True) 跳过——那正是 §2.6.3 里 mlp_reduce_scatter scoped 标记的用途：DP attention 下由 combine 之后的 reduce_scatter 一并完成归约，避免双归约。
  3. TP1 shared 的后置相加：shared expert 没做 TP 切分时（_shared_expert_tp1），每个 rank 算出的 shared 输出完全相同，所以它被安排在 all-reduce 之后才相加，否则会被归约重复累加 tp_size 次。注意第 1 步传给 maybe_fuse_routed_scale_and_shared_add 的 shared 这时是 None（deepseek_v2.py:1371），正是为了把这次相加推迟到这里。

为什么归约放在模型层，而不是 MoE 层内部？可以看到， FusedMoE.reduce_results 的传参默认是 False，forward_impl 里的兜底 all_reduce 只在显式配置时才触发（fused_moe_triton/layer.py:1596-1597）。这是因为，MoE 层“身在此山中”，它要处理太多地细节，看不清上层用的是 TP-MoE 还是 EP，更不知道 attention 侧的并行形态（EP 的跨 rank 归约已经在 combine 里做完，DP-attn 有 reduce_scatter ）；故只能把“要不要归约、归约哪一组”交给最了解并行形态的 deepseek_v2 模型层决定，才不会出现 EP 与 all_reduce 各做一遍、或者 DP-attn 与 all_reduce 重复归约的错误。

2.6.3 V4 的 DP attention 变体：_run_moe_ffn_dp_sync

之前小节对 MoE 的叙述有一个隐含前提：本 rank 手上的 token 就是这层 MoE 要算的全部 token。然而，在 DeepSeek V4 在 attention 数据并行（attn DP）× MoE 张量/专家并行下打破了这个前提——当每个 rank 只有自己算出来的部分 token 时，expoerts 不论是按 intermediate 切在 TP 上（单卡只算出半个 MLP），还是按 EP 切在不同 rank 上，都是没办法准确计算了。于是 DeepSeek V4 在每层 MoE 前向上又加了一层抽象，将 MoE 整体收进 _run_moe_ffn_dp_sync，由它决定“进 MoE 前怎么把 token 凑齐、出 MoE 后怎么把结果还回去”。

三条形态互斥，判定都带 not _use_cp：

形态 MoE 之前 MoE 之后 归约落在哪
TP-MoE + attn DP（_use_tp_moe_gather） dp_gather_replicate 拼全局 token reduce_scatterv / 等分片 reduce_scatter / dp_scatter 回程的 reduce_scatter；MoE 内部 all_reduce 被 mlp_reduce_scatter=True 跳过
EP + attn TP（_use_tp_attn_a2a_scatter） 按 attn_tp_rank 把 token tensor_split 一份给本 rank attn_tp_all_gather 拼回 EP 的 all2all 里；尾部只 gather、不再 reduce
CP（_use_cp） a2a==none 走 dsa_cp_gather_hidden_states，否则直接 all2all dsa_cp_reduce_scatter_hidden_states CP 分片的 reduce_scatter

三者都不命中时，可以是纯 TP-MoE，函数退化成一次裸的 self.mlp(...)，前后不加任何搬运——因为这时 token 就全在本 rank，各 TP rank 算完自己的专家分片后交给 post_experts_all_reduce 求和即可。如果 EP + DP，且 attn_tp_size=1，那没有 gather、没有 split、没有 reduce_scatter。因为在这个配置下每个 rank 手上的 token 是自己的、且完整的，不同 rank 的 token 互不重叠。

1）TP-MoE + attn DP：先 gather 全局 token，再 reduce_scatter 还回去

TP-MoE 下专家按 intermediate 维切在 TP 组上，单卡只算出 MLP 的一部分和，所以必须“所有 token 都过一遍所有 rank 上的 experts”，然而因为 attn DP ，每个 rank 都只有一部分 token，所以方法就是先把 token gather 都拿回来：

注意这里必须是“复制”语义的 gather 而不是 partial-sum：因为 self_attn 已经在 attention TP 上 all_reduce 过，各 rank 的 hidden 其实是同一份 tensor 的不同部分。

在结束阶段， reduce_scatterv 则是同一个道理的反向：一次算子完成“跨 TP reduce 求和，再把 token 切片各自拷贝到对应 shard 回去”，好让各个 rank 继续下一层的计算，这两个操作合并到一起就是 reduce scatter。当然，此时 MoE 内部的 post-experts all_reduce 必须被跳过，否则就多算了一次。

mlp_reduce_scatter 正是 §2.6.2 里 should_skip_post_experts_all_reduce(is_tp_path=True) 读到的那个 per-forward 标志——一边写、一边读，靠 get_forward() 的 scoped 上下文传递。

三条回程按能力从强到弱排：

  1. reduce_scatterv：变长的 gatherv/scatterv 配对，分片长度由 get_dp_global_num_tokens() 给出。前提是 SGLANG_DP_USE_GATHERV（默认关）、SUM_LEN padding、attn_tp_size == 1 且 tp_size == attn_dp_size（is_dp_gatherv_active，dp_attention.py:793-810），否则两边长度对不上，直接调用 pynccl_comm.reduce_scatter(output, input_, sizes=sizes)
  2. 等分片 reduce_scatter：MAX_LEN（各 rank 等长 padding、gatherv 不生效）时走这条，开关是 SGLANG_DP_USE_REDUCE_SCATTER，要求 tp_size == attn_dp_size， 调用 pynccl_comm.reduce_scatter(output, input)
  3. dp_scatter：兜底。这时 mlp_reduce_scatter 为 False，MoE 内部 all_reduce 照常做，那就相当于先 all_reduce，再拷贝本 rank 切片。

顺带一个可选优化：SGLANG_DP_SHARED_EXPERT_LOCAL（deepseek_v4.py:368）打开且 shared expert 是 replicated（TP1）时，shared 的输出改成在 gather 之前只用本地 token 算（deepseek_v4.py:3837-3838），等回程之后再加到本 rank 切片上（deepseek_v4.py:3902-3907）。shared expert 是逐 token 的 MLP，“在 M_local 行上算”与“在 M_global 行上算完再取切片”结果一致，但前者只要 1/dp_size 的行数——这正是 §2.6.2 第 3 点“TP1 shared 在归约之后相加”那份代价的补丁。

2）EP + attn TP：token 均分给各 rank，回程 all_gather

EP 下 experts 切在不同 rank 上，token 由 dispatch/combine 的 all2all 自己找到对应的 rank，不需要 gather 全局；但 attn TP 组内每个 rank 握着同一批 token ，让每个 rank 都把全量 token 来跑一遍 MoE 纯属浪费，为此，按 attn_tp_rank 把 token 均分成 attn_tp_size 份、每个 rank 只留一部分 token shard（deepseek_v4.py:3843-3846），回程 attn_tp_all_gather 拼回（deepseek_v4.py:3908-3912）。

回程只 gather、不 reduce，是因为每份切片算出的都是完整结果（该 token 的 top-k 专家输出已由 combine 求和），只是分散在不同 rank 上。

细节：input_ids / input_ids_global 要跟着一起切（deepseek_v4.py:3849-3852）。V4 有按 token id 路由的 hash MoE 层（deepseek_v2.py:1871-1877），路由依据和 token 一旦错位就全错；而 DSpark 这类不带 id 的层则是“有就切、没有就跳过”。

3）CP：用 CP 专用 gather 或直接走 all2all

CP（prefill context parallel）把一条序列按 context 切成几段放在不同 rank 上，所以 _use_cp 为真时上面两条都不成立，MoE 前必须把 token 汇聚：a2a == none 用专用的 gather dsa_cp_gather_hidden_states；走 all2all 则要求 moe_a2a_backend ∈ {deepep, megamoe, mori}（断言 deepseek_v4.py:3824-3831）——因为只有这几个后端有“按 token 送去专家”的能力。

reduce scatter 部分也有专用的 dsa_cp_reduce_scatter_hidden_states。专用的 all gather 和 reduce scatter 都是按照 rank 拼接到了 hidden states tensor 内。每个 CP rank 的真实行都落在自己那段 slot 里，不是整个缓冲的前缀，所以在 a2a==none 时，因为 CP 下 gather 后的缓冲是按 CP rank 拼的，真实行是所有的行，而非仅仅前 N 行，所以必须在 MoE 期间把有效行数设成整块缓冲大小，否则 router 的前缀掩码会误删后面 rank 的真实 token。

所以对 DeepSeek V4 在 Blackwell 上用 DeepEP 的典型部署（attn 侧 TP、MoE 侧 EP）：先切掉 attn TP 组内重复的 token 副本，再交给 DeepEP 做 all2all，最后 all_gather 拼回来；而 DeepEP 这一层内部实际执行的仍然是 §2.4/§2.5 讲的 DeepGEMM MoE 中的三段式。

总结一下，不同并行方式下 MoE 相关的 token 通信和内存行为：

并行方式 MoE 前 dispatch combine MoE 后
attn TP × TP-MoE 纯 TP — 本地重排 本地加权 1 次 all_reduce
attn DP × TP-MoE gather 成全量 本地重排 本地加权 1 次 reduce_scatter
attn TP × EP 切掉重复副本 all2all 发出 all2all 收回 1 次 all_gather
attn DP × EP — all2all 发出 all2all 收回 —

3.6.1 get_mn_major_tma_aligned_tensor

把普通权重/激活 scale 转成 MN-major、TMA 对齐布局，非 UE8M0 平台激活侧调用。

docstring 里记录了仓库作者遇到的 use-after-free 事故并做了防御（:25-36）：sgl-deep-gemm 的快速路径在「输入已是目标布局」时会跨 TVM-FFI 返回一个 非持有（non-owning）的 from_blob 别名；而调用方习惯写 x = get_mn_major_tma_aligned_tensor(x)——重绑结果后原存储被释放，GEMM 仍透过别名读取，一旦 allocator 复用该块就是 UAF（表现为 NaN logits 或 CUDA graph capture 期的 “pointer resides on host memory”）。wrapper 因此检测 out.data_ptr() == sf.data_ptr() 时直接返回原 tensor 以保住所有权。

7. 小结

  • 一副骨架：dispatch → pre_permute → DeepGemmRunnerCore.run → post_permute → combine。DeepGEMM runner 的全部差异都收敛在 pre/post_permute 的布局转换与 core 的四个 GEMM 分支里；
  • 两个正交开关：布局（masked / compact）× 配方（bf16 / fp8 / mxfp8 / mxfp4）。dispatcher 决定 pre/post_permute 的实现；权重类型与 DeepGemmMoeQuantInfo 决定 core 的走向；
  • 接口分三层：模型层（DeepGemmRunnerInput/QuantInfo）→ runner core（shape 推导、recipe、激活量化）→ wrapper（entrypoint.py 八个接口：sanity check、execution hook、num_sms 管理）→ deep_gemm 库（JIT 编译的 grouped/dense GEMM）。每层的参数职责在 §3 逐一展开；
  • Blackwell 的实质变化：UE8M0 int32 packed scale（MN-major TMA）与 FP4/MXFP8 配方。SGLang 在加载期就把权重与权重 scale 整理成 deep_gemm 最终消费的布局（requant / transform / pack），运行期只负责激活侧量化与布局重排（§2.1、附录 A）；
  • V4 的特有之处：MoE 复用 DeepseekV2MoE；is_fp4_experts 默认打开（recipe (1,128)/(1,32)）；swiglu_limit 存在（走 V4 JIT 激活）；DP attention 下有 _run_moe_ffn_dp_sync 协调 gather/scatter 与 all_reduce 的替代关系（§2.6.3）。

附录 A：UE8M0——从 fp32 到 int32 packed 的三条生产线

UE8M0 是只保留指数的 8-bit 浮点（无尾数、无符号，值域即 2 的幂），deep_gemm 要求 scale 以 MN-major、TMA 对齐、4 个 uint8 打包进 1 个 int32 的形式存储。样本分别来自三条生产线：

  1. 权重加载期（fp4 → UE8M0）：transform_sf_into_required_layout(recipe=(1,32), disable_ue8m0_cast=False)，两条调用线——fp8 量化方法的 is_fp4_expert 分支（fp8.py:2056-2074）与纯 MXFP4 量化方法（mxfp4.py:650-674，先经 float8_e8m0fnu → float32 的精确往返）；库内完成 cast + 布局重排；
  2. 权重加载期（fp8-block / mxfp8）：requant_block_scale_ue8m0_for_deepgemm（fp8_utils.py:1719-1750）→ transform_scale_ue8m0（fp8_utils.py:1854-1878）；调用点 fp8.py:2085-2098；mxfp8 的 _pack_moe_scale_for_deepgemm（fp8.py:2248-2262）同款；
  3. 运行期激活量化：
    • contig silu 融合：silu_and_mul_contig_post_quant(scale_ue8m0=UE8M0, transposed=UE8M0)，scale 缓冲由 create_per_token_group_quant_fp8_output_scale(column_major_scales=UE8M0, scale_tma_aligned=UE8M0, scale_ue8m0=UE8M0) 直接按 packed 布局分配（deep_gemm.py:530-552）；
    • masked silu：per_token_group_quant(scale_ue8m0=UE8M0, column_major_scales=True) 自带 packed 布局输出（deep_gemm.py:1635-1643，注释说明调用方的 get_mn_major transform 会短路）；
    • masked situ 三分支：JIT kernel 输出后补 transpose(-1,-2)（deep_gemm.py:1528 / 1595 / 1627）；
    • 兜底：_cast_to_e8m0_with_rounding_up（deep_gemm.py:96-106；调用点 :501 contig、:747 masked）。

_cast_to_e8m0_with_rounding_up 的位运算：把 fp32 看成 int32，取指数位 exp = bits >> 23、尾数 mant = bits & 0x7FFFFF；当「尾数非零且指数非 0xFE（inf/nan 保护），或指数为 0 时尾数足够大」时指数 +1（round up），再取低 8 位作为 uint8，最后 transpose(1,2).contiguous().transpose(1,2) 转 MN-major 对齐。这也是 _sanity_check_input 断言「fp32 scale 必须已是 2 的幂」的原因——非 2 的幂会被 round-up cast 改变数值。

附录 B：masked 还是 compact——自动选择的过滤链

_should_use_masked_standard_layout（deep_gemm.py:196-249）依次过滤：

  1. SGLANG_OPT_DG_COMPACT_EAGER=1 且非 capture → 强制 compact（逃生舱）；
  2. _masked_activation_unsupported_reason（:175-193）给出理由 → compact。理由只在「clamped/swizzled 激活」（swiglu_limit 存在或 megamoe）下出现，条件为 D//8 < E、group_size != 128、D % (4*group) != 0 之一（DSV4 JIT kernel 的硬约束）；
  3. 环境变量 SGLANG_DEEPGEMM_STANDARD_LAYOUT：masked / compact 直接定夺；auto 继续；
  4. auto：CUDA Graph capture 中 → compact（capture 内不能查显存）；否则估算 masked 峰值（_estimate_masked_standard_layout_peak_bytes :132-167：E × padded_m × 单行峰值字节，单行峰值取三项差的最大值）与预算 min(free_memory) × SGLANG_DEEPGEMM_MASKED_MEMORY_BUDGET_FRACTION 比较——放得下就 masked，放不下就 compact。

几何对比：masked 用 (E, m, K) slab + masked_m/expected_m，workspace 是 E × padded_m 量级；compact 用 (all_tokens, K) + m_indices/src2dst，all_tokens 由 _get_compact_all_tokens（:252-259）给出上界：block_e × (非空 expert 数 + 剩余 tokens 摊入的块数)。

附录 C：ep_scatter 家族与三个索引

布局重排的底层 kernel（kernels/ops/moe/ep_moe_kernels.py）按场景分三支：

  • ep_scatter：standard compact / deepep_normal 使用——按 tokens_per_expert（或 recv 计数）把 token 与激活 scale 散进 expert 连续段，同时产出 m_indices（行→expert）与 src2dst/output_index（回程映射）；expert_alignment=block_e 保证每 expert 段按 GEMM 对齐要求 padding；
  • ep_scatter_from_psum：deepep_v2 非 expanded 分支，用原生 psum 前缀和替代计数数组；
  • moe_ep_deepgemm_preprocess（masked）：一步融合「路由分桶 + slab 填充 + 激活量化」，直接产出 (E, m, K) 与 src2dst。
